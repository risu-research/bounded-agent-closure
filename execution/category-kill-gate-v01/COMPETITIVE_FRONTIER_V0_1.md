# Competitive Frontier v0.1 — 2026-09-04

Status: STRATEGIC SOURCE AUDIT — NOT A PROJECT X RESULT

## Decision

The existence of a consequence/outcome-assurance problem is **not** a defensible Project X novelty claim in September 2026.

Multiple independent systems now occupy adjacent or overlapping territory. That is external validation of the problem, but it raises the burden for Project X.

The differentiating thesis is narrowed to **integration compression**:

> Given a new consequential interface, Project X must derive a typed, executable, bounded evidence-acquisition plan from the intended consequence plus machine/interface documentation with very little or no provider-specific semantic programming.

If Project X requires a manually maintained provider/resource rule catalog with comparable labor to existing systems, the horizontal infrastructure thesis is killed.

## Frontier A — RecourseOS

Sources:

- https://recourseos.com/
- https://recourseos.com/docs
- https://recourseos.com/docs/depth-advantage

Observed frontier:

- explicitly calls itself consequence verification for autonomous systems;
- normalizes mutations into a universal consequence contract;
- queries live infrastructure state;
- emits machine-readable ConsequenceReports and signed attestations;
- claims 175+ resource types with deterministic resource-specific handlers;
- unknown resources use semantic classification with conservative escalation.

What this invalidates for us:

- `consequence verification` as a category-name novelty claim;
- signed evidence reports as a moat by themselves;
- generic MCP/CLI/CI integration as a moat;
- a provider-specific handler catalog as an ambitious enough architecture.

Open differentiation target:

- RecourseOS publicly describes deep deterministic rules for known resource types and a semantic fallback for unknowns. Project X must demonstrate that a new interface can be integrated by **compiling evidence obligations and acquisition plans**, not by adding another handcrafted handler.

## Frontier B — Provy

Source: https://provy.ai/

Observed frontier:

- markets `Outcome Assurance for autonomous AI`;
- reconciles agent runs against real outcomes/business results;
- asks users to define what `done right` means;
- maps those conditions to signals and grades runs condition-by-condition;
- provides attribution, reliability, and fix verification.

What this invalidates for us:

- `real outcome, not trace` as a unique slogan;
- post-run reconciliation alone as a moat;
- generic cross-workflow positioning alone as a moat.

Open differentiation target:

- Project X must reduce or eliminate the manual semantic mapping from `done right` to trustworthy signals and stopping conditions.

## Frontier C — RAILS

Sources:

- https://arxiv.org/abs/2606.08790
- https://github.com/Evolutionairy-AI/RAILS

Observed frontier:

- explicitly states that authorization, payment, settlement, and LLM-as-judge do not determine whether delegated obligations were met;
- defines Obligation Object, Evidence Envelope, Verification Mesh, Clearing Decision, Settlement Instruction, Clearing Passport, and Finality Rules;
- introduces admissibility-graded evidence and a formal soundness property;
- includes a reference implementation and adversarial harness.

What this invalidates for us:

- `authorization is not consequence` as a novel research thesis;
- formal evidence grading alone as a moat;
- obligation/evidence/finality data structures alone as a moat.

Open differentiation target:

- RAILS' obligation object includes acceptance criteria and required evidence. Project X must test whether those evidence requirements can themselves be **derived from the target consequence and interface semantics**, instead of being authored upstream.

## Frontier D — ConsequenceBench / governance benchmarks

Source: https://github.com/yuvin-labs/consequencebench

Observed frontier:

- product-neutral benchmark for authority, evidence, retries, readback, delayed consequences, obligations, compensation, and unsafe effects;
- evaluator-owned worlds and deterministic oracles;
- paired direct-vs-governed studies;
- explicit requirement for independent readback and reproducible evidence.

What this invalidates for us:

- a small synthetic consequence benchmark as a moat;
- `independent readback matters` as a unique insight;
- self-authored benchmark wins as strong market evidence.

Open differentiation target:

- Project X should be evaluated as a candidate compiler/governance mechanism on external or prospectively selected tasks rather than relying on RISU-authored fixtures.

## Strategic moat hypothesis — narrowed

Project X is retained as a horizontal thesis only if it can show a different scaling law:

### Existing/catalog scaling law

`new provider/resource/workflow -> human semantic analysis -> bespoke handler/rules -> tests -> maintenance`

### Project X target scaling law

`new consequence + machine-readable interface/docs -> consequence compiler -> typed evidence obligations -> executable evidence plan -> bounded verifier`

with only a small, provider-neutral trust/configuration surface.

## Kill criterion C-K1 — Catalog Equivalence

**KILL-HORIZONTAL** if a new held-out system requires any of the following to reach a correct executable evidence plan:

- a new generic consequence/evidence primitive;
- more than 2 provider-specific semantic annotations in the median case;
- a provider/resource-specific procedural handler whose control flow is not generated from the interface/evidence contract;
- manual endpoint/field/stopping-condition selection comparable to a conventional integration;
- an LLM-authored plan that cannot be deterministically validated against a typed plan schema and source contract.

## Kill criterion C-K2 — Baseline Parity

**KILL-HORIZONTAL** if a strong LLM using the same public docs can, without Project X concepts, produce equally executable and source-correct evidence plans on >= 7/8 frozen category cases **and** on the prospective holdout set with no materially worse robustness under prompt/model variation.

The reason is economic rather than academic: if `LLM + ordinary code` already gives the same integration cost and safety, there is no demonstrated infrastructure layer to sell.

## Positive criterion C-P1 — Zero-Shot Integration Compression

A strong Project X candidate must show on unseen holdouts:

1. no provider-specific procedural code written after holdout reveal;
2. <= 2 provider-specific semantic annotations per case median;
3. a concrete typed plan naming real endpoint/operation, object relation, field/predicate, pagination/completeness boundary when relevant, temporal/retry boundary, and stopping condition;
4. zero unsupported decisive consequence claims;
5. deterministic validation of the compiled plan;
6. materially lower new-system semantic work than the catalog baseline;
7. failure to compile must produce an exact missing capability/evidence requirement, not a guessed plan.

## Position if C-P1 passes

Do **not** sell `consequence verification` generically.

The sharper category candidate becomes:

> **Consequence Contract Compiler** — compile an intended real-world/system consequence into the minimal executable evidence program required to prove it, or a machine-readable statement of why it cannot currently be proved.

Verification, receipts, audit, and outcome scoring become downstream consumers of the compiler rather than the category definition.
